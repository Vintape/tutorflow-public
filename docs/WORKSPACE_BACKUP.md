# Холодная копия локального TutorFlow workspace

13 ноября 2026. Утилита: `scripts/workspace-backup.ts`. Проверки — только на новых синтетических данных. Копия или восстановление исходной пользовательской базы этим этапом **не выполнялись**.

## Область действия

Локальный workspace состоит из двух связанных хранилищ: файловой CRM PGlite и `BOARD_DIR` с авторитетными native SQLite досок. `scripts/cold-backup.ts` остаётся прежним инструментом CRM; его копия не включает доски. Новый инструмент захватывает оба хранилища в одной остановленной границе.

Поддерживаются только установленные PGlite **0.5.15**, tldraw / sync-core / tlschema **5.6.0**, canonical board envelope v1 и native SQLite migrationVersion 3. `--source-project` задаёт проект, из которого работал остановленный сервер: проверяются установленные версии, а не только декларации зависимостей. Хеши всех его SQL-миграций должны совпадать с текущими проверенными файлами утилиты и с `_migrations` в новой проверочной копии. Миграции утилита не применяет.

**Внешний PostgreSQL не поддерживается этим файловым архивом.** Если действующая CRM использует `DATABASE_URL`, выбор папки PGlite не создаёт копию PostgreSQL и не доказывает полноту workspace. Нужны отдельно разрешённые операции dump/restore PostgreSQL, согласованная остановленная граница с `BOARD_DIR` и отдельная проверка восстановления. Таких операций эта утилита не выполняет и доступ к серверу PostgreSQL не открывает. Она не загружает `.env` или настройки приложения.

## Безопасная граница

Перед реальной операцией требуется отдельное разрешение владельца на штатную остановку действующего сервера, чтение и копирование его данных и, при необходимости, auth-secret. Текущая автономная инженерная миссия такого разрешения не заменяет. Утилита сама не останавливает сервер, не завершает чужие процессы и не удаляет старые блокировки.

Все писатели должны пользоваться серверными блокировками. Утилита удерживает одновременно те же `proper-lockfile` locks CRM и BoardRuntime до окончания копирования, проверки файлов и формирования манифеста. Любая существующая блокировка, включая старую, или `postmaster.pid` вызывает отказ. SQLite источника не открывается даже для чтения: захватываются все файлы, включая оставшиеся после остановки WAL/SHM, историю, ledger и intent. В текущем формате история, Python ledger и intent находятся внутри SQLite; дополнительные обычные файлы также сохраняются. Произвольный внешний писатель, обходящий эти блокировки, не является поддерживаемым способом работы.

Каталоги источников и назначения должны быть раздельными. Назначение и его родитель выбираются явно; родитель должен уже существовать. Утилита не перезаписывает существующее назначение. Новые каталоги имеют `0700`, файлы — `0600`. Символьные ссылки, FIFO, устройства и недопустимые пути отвергаются; таблицы PostgreSQL с внешними symlink tablespaces не поддерживаются.

Архив содержит `crm/`, `boards/`, необязательный `auth-secret`, `manifest.json` и `manifest.sha256`. Версионированный манифест перечисляет все файлы и каталоги, размеры, SHA-256, версии движков, SQL-миграции и соответствие metadata состояниям досок/сохранённым версиям. Сам манифест не содержит текстов формул, Python, заметок, паролей или bearer-секретов. Архив содержит приватные исходные данные в открытом виде: права доступа не являются шифрованием.

`--auth-secret` отсутствует по умолчанию. Он копирует только явно выбранный файл побайтно с `0600`; `.env`, провайдерские ключи, demo-login и другие секреты автоматически не собираются. Без этого файла оператор отдельно выбирает корректную конфигурацию авторизации восстановленного приложения. Содержимое секретов и исходные тексты не выводятся. CLI сообщает только статус, код отказа, хеш заголовка и агрегированные счётчики.

## Команды после отдельного разрешения

Ниже шаблон, а не выполненная операция. Заменить пути на явно согласованные локальные источники; не использовать действующую исходную базу без отдельного разрешения. До выполнения проверить, что CRM действительно PGlite, `BOARD_DIR` соответствует этому же workspace и сервер штатно закрыл оба хранилища. Нельзя удалять `.lock` или `postmaster.pid` для обхода отказа.

Из проверенного checkout создать **новый** приватный родительский каталог, затем выполнить:

```sh
mkdir -m 700 /path/to/new-private-recovery

sh scripts/tutorflow.sh exec tsx scripts/workspace-backup.ts backup \
  --source-project /path/to/stopped-source-project \
  --crm /path/to/approved-cold-pglite \
  --boards /path/to/approved-cold-board-dir \
  --destination /path/to/new-private-recovery/archive-01
```

Если отдельно согласовано включение auth-secret, добавить `--auth-secret /path/to/approved-auth-secret`. Успешная команда возвращает `status: workspace-backup-created`, `manifestSha256` и счётчики. Записать возвращённый SHA-256 отдельно от архива: он является обязательным внешним контрольным значением для проверки. `manifest.sha256` внутри архива не заменяет сохранённый внешний хеш и не является подписью.

После успешного завершения команды все её блокировки освобождены. Если разрешён возврат исходного сервиса, его можно штатно запустить с прежней конфигурацией. Проверка восстановления дальше читает архив, а не работающий исходный workspace.

```sh
sh scripts/tutorflow.sh exec tsx scripts/workspace-backup.ts verify \
  --archive /path/to/new-private-recovery/archive-01 \
  --destination /path/to/new-private-recovery/restore-check-01 \
  --manifest-sha256 EXACT_DIGEST_RETURNED_BY_BACKUP
```

Назначение проверки также должно быть новым. Команда не запускает сервер, не заменяет исходные папки и не публикует восстановленное приложение. При отказе проверочная копия удаляется; исходные файлы и архив сохраняются. При жёстком прерывании питания/процесса может остаться неполный новый каталог без успешного результата: не использовать его и не обходить проверку. Повторная проверка выполняется из архива в другое свежее назначение.

## Что означает успешная проверка

До первого SQL-открытия сверяются внешний хеш заголовка, версии, полный состав и все SHA-256 архива, затем побайтный состав новой копии. Проверяющий процесс блокирует архив и оба его хранилища; источник и архив не открываются как базы. На новой копии CRM выполняются `READ ONLY` проверки SQL-миграций и связей владельцев/досок/учеников/уроков/гостей. SQLite новой копии открывается с `readOnly: true`: проверяются целостность, native init/schema, канонические записи с SDK-валидацией, Python revisions, сохранённые версии и lesson snapshot references.

ACTIVE обязательно имеет существующий, полностью инициализированный файл. Отсутствующий или пустой файл не превращается в новую доску. CREATING сохраняется без активации: допустимы отсутствующий файл, сохранённый intent или уже готовый native файл; это незавершённая операция, не готовый материал для гостя. DELETED сохраняет tombstone и недоступность; оставшиеся файлы сохраняются непрозрачно, без восстановления доступа. Они не считаются проверенной ACTIVE-доской. Неизвестные native SQLite без соответствующей metadata отвергаются. Никакое состояние не удаляется или исправляется на источнике.

После успешной проверки целостности **только в новой копии**, под её блокировками и транзакционно:

- отзываются все старые board invitations и guest sessions;
- очищаются старые owner login sessions;
- сохраняются аккаунты, пароли владельцев, материалы, история и CRM/lesson links.

Это не позволяет исторической копии возродить ссылку или сессию, отозванную после её создания. Владелец заново входит и при необходимости выпускает новые гостевые ссылки. Архив сохраняет первоначальные данные для проверки, его секреты и сессии не изменяются. Результат явно содержит `guestAccess: revoked`, `ownerSessions: cleared`. Восстановленная CRM вследствие этой политики уже не побайтная копия архива; проверки каталогов и хешей выполняются до финализации.

Переключение реального сервиса на новую копию, удаление старого workspace, изменение конфигурации/секретов и любое production-восстановление — отдельные операции с разрешением владельца и собственным планом возврата. Успех на синтетике не является проверенной копией пользовательской базы, полной аппаратной проверкой всех индексов PostgreSQL или гарантией production disaster recovery.

## Воспроизводимая проверка

```sh
sh scripts/tutorflow.sh exec vitest run tests/workspace-backup.test.ts tests/backup.test.ts
sh scripts/tutorflow.sh typecheck
sh scripts/tutorflow.sh exec eslint scripts/workspace-backup.ts tests/workspace-backup.test.ts
```

Fixtures создаются только в новых `tutorflow-workspace-backup-*` внутри системного tmpdir. Сценарий создаёт настоящий CRM аккаунт/ученика/урок, BoardService links/invites и BoardRuntime SQLite с формулой, Python и историей; штатно закрывает оба хранилища; создаёт архив; удаляет только синтетический источник; затем поднимает восстановленное приложение на свободном loopback-порту и проверяет вход владельца, источники, историю и ссылки. Старые гостевые секреты отклоняются. Отдельно проверяются неизменность источника/архива, обе live locks, stale lock, повреждение/неполная копия, отсутствующая ACTIVE SQLite при согласованных хешах, версии, коллизии, ledger/init/history, пути и отсутствие секретов в CLI. Старые cold-backup CLI тесты сохраняются.

Ограниченные приватные журналы RED/GREEN и результатов находятся в `.data/mission-evidence/workspace-backup/`; они не включаются в Git. Остальные агенты и root выполняют общий suite и browser E2E отдельно; эти проверки не заявляются результатом данного инструмента.
